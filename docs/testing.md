# Testing

## Why these test types?

Spring Boot applications have multiple layers, and each layer has different testing needs. Using the right test type for each layer keeps tests **fast, focused, and trustworthy**.

```
                      Scope           Speed       Spring context
                      ─────────────   ─────────   ──────────────
Unit tests            Single class    Very fast   None
Repository tests      DB layer only   Fast        Partial (JPA slice)
Controller tests      HTTP layer      Fast        Partial (MVC slice)
Integration tests     Full app        Slow        Full
```

This project follows this pyramid: many unit tests at the base, fewer but more realistic integration tests at the top.

## Unit tests (Mockito)

**Location:** `service/impl/`, `security/`, `scheduler/`, `dto/auth/`, `validation/`, `mapper/`

**Annotation:** `@ExtendWith(MockitoExtension.class)`

Unit tests isolate a single class by mocking all its dependencies with `@Mock`. They run without Spring and without a database, making them very fast.

**Example:** `CategoryServiceImplTest` mocks `CategoryRepository` and `CategoryMapper`. It verifies that `findById` throws `ResourceNotFoundException` when the repository returns empty - without touching a real database.

```java
@ExtendWith(MockitoExtension.class)
class CategoryServiceImplTest {
    @Mock CategoryRepository categoryRepository;
    @Mock CategoryMapper categoryMapper;
    @InjectMocks CategoryServiceImpl categoryService;

    @Test
    void _02_ShouldThrowNotFound_WhenCategoryMissing() {
        when(categoryRepository.findById(99L)).thenReturn(Optional.empty());
        assertThatThrownBy(() -> categoryService.findById(99L))
            .isInstanceOf(ResourceNotFoundException.class);
    }
}
```

**When to use:** business logic, service rules, exception cases, edge cases.

## Repository tests (@DataJpaTest + Testcontainers)

**Location:** `repository/`

**Annotations:** `@DataJpaTest`, `@AutoConfigureTestDatabase(replace = NONE)`, `@Import(RepositoryTestcontainersConfiguration.class)`

`@DataJpaTest` is a **Spring slice**: it loads only the JPA layer (entities, repositories, Flyway) without controllers or services. This is much faster than a full application context.

The critical choice here is `@AutoConfigureTestDatabase(replace = NONE)` combined with Testcontainers. By default, `@DataJpaTest` would try to replace the datasource with an in-memory H2 database. We override this to use a **real PostgreSQL container** instead.

**Why not H2?** PostgreSQL and H2 have different SQL dialects. For example:
- PostgreSQL's `CHECK (email ~* '...')` (regex constraint) has no H2 equivalent
- PostgreSQL's `GENERATED BY DEFAULT AS IDENTITY` behaves differently from H2's `AUTO_INCREMENT`
- Flyway migrations written for PostgreSQL may fail on H2

Using a real PostgreSQL means what passes in tests will work in production.

```java
@DataJpaTest
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)
@Import(RepositoryTestcontainersConfiguration.class)
class CategoryRepositoryTest {
    @Autowired CategoryRepository categoryRepository;
    // Flyway runs migrations against the Testcontainers PostgreSQL
}
```

**`RepositoryTestcontainersConfiguration`** declares a `PostgreSQLContainer` bean annotated `@ServiceConnection`. Spring Boot's `@ServiceConnection` automatically wires the container's JDBC URL, username, and password into the test's datasource - no manual property overriding needed.

**When to use:** custom `@Query` methods, derived queries, `@EntityGraph` behavior, Flyway migration correctness.

## Controller tests (@WebMvcTest)

**Location:** `controller/`

**Annotations:** `@WebMvcTest(XxxController.class)`, `@MockitoBean` for services

`@WebMvcTest` is another Spring slice: it loads only the web layer (controllers, filters, security config) without services or repositories. Services are replaced by `@MockitoBean`, which creates a Mockito mock and registers it as a Spring bean.

```java
@WebMvcTest(CategoryController.class)
class CategoryControllerTest {
    @Autowired MockMvc mockMvc;
    @MockitoBean CategoryService categoryService;
    // JwtAuthFilter also needs these to construct (see note below):
    @MockitoBean JwtService jwtService;
    @MockitoBean UserDetailsService userDetailsService;
    @MockitoBean BlacklistedTokenService blacklistedTokenService;
}
```

> **Important:** Spring Boot includes every `Filter` bean in `@WebMvcTest` slices, even those unrelated to the controller under test. `JwtAuthFilter` depends on `JwtService`, `UserDetailsService`, and `BlacklistedTokenService`. All three must be mocked even in controller tests that never send a JWT, or the slice will fail to build.

**When to use:** HTTP status codes, JSON serialization, `@Valid` validation, request mapping, response body shape.

## Integration tests (Testcontainers + full context)

**Location:** `controller/SecurityAuthorizationTest.java`, `service/impl/CategoryServiceCacheTest.java`, etc.

**Annotations:** `@SpringBootTest`, `@AutoConfigureMockMvc`, `@Import(SecurityTestcontainersConfiguration.class)`

`@SpringBootTest` loads the complete application context - every bean, filter, and configuration class, with Testcontainers providing the real PostgreSQL. These tests are slower but test real behavior end to end.

`SecurityAuthorizationTest` is the main integration test suite. It exercises the real `SecurityFilterChain` with real JWTs:

```java
// Register -> enable account -> login -> extract real JWT -> call protected endpoint
MvcResult loginResult = mockMvc.perform(post("/api/v1/auth/login") ...)
    .andReturn();
String token = objectMapper.readTree(loginResult.getResponse().getContentAsString())
    .path("data").path("access_token").asText();

mockMvc.perform(get("/api/v1/customers").header("Authorization", "Bearer " + token))
    .andExpect(status().isOk());
```

This kind of test cannot be replaced by unit or slice tests: it verifies that the security rules declared in `SecurityConfig` are actually enforced by the real filter chain, not by a mock assumption.

**When to use:** security rules, full flows (register/activate/login/logout), cache behavior, event publishing.

## Test naming convention

Every test method follows this pattern:

```
_NN_Should<Outcome>_When<Condition>
```

- `NN` is a zero-padded sequence number, starting at `01` in each class
- `<Outcome>` describes what the method returns or does
- `<Condition>` describes the input state

Examples:
```java
_01_ShouldReturnCategory_WhenCategoryExists()
_02_ShouldThrowNotFound_WhenCategoryMissing()
_03_ShouldReturn400_WhenCategoryNameIsBlank()
```

The numbered prefix ensures tests appear in a predictable, readable order in the IDE's test runner, even though JUnit 5 does not guarantee execution order.

## Running the tests

```bash
# Run the full test suite
JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64 ./mvnw clean test

# Run a single test class
JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64 ./mvnw test -Dtest=CategoryServiceImplTest

# Run with explicit Docker socket (if Testcontainers can't find Docker)
DOCKER_HOST=unix:///home/<user>/.docker/desktop/docker.sock \
  JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64 ./mvnw clean test
```

> If Testcontainers fails with `Could not find a valid Docker environment` but `docker info` works from the terminal, Docker Desktop is using a non-default socket. Set `DOCKER_HOST` to the Docker Desktop socket path and retry.

## Known test design decisions

### No H2, only Testcontainers

There is no H2 dependency in `pom.xml`. All repository and integration tests use a real PostgreSQL container. The tradeoff: tests take longer to start (container spin-up), but they never produce false positives from dialect differences.

### @WebMvcTest with addFilters=false does NOT remove JwtAuthFilter

`@AutoConfigureMockMvc(addFilters = false)` prevents filters from executing during the request, but Spring Boot still includes every `Filter` bean in the application context for `@WebMvcTest`. `JwtAuthFilter` will still be instantiated and needs its dependencies mocked.

### Cache isolation between tests

`@SpringBootTest` reuses the same application context (and the same `CacheManager`) across all test methods in a class. Without explicit cache clearing, a cached result from one test can affect the next. `CategoryServiceCacheTest` and `ProductServiceCacheTest` clear the cache in `@BeforeEach`:

```java
@BeforeEach
void clearCache() {
    cacheManager.getCache("categories").clear();
}
```

### @DataJpaTest requires JpaAuditingConfig for tables with audit columns

`Category` has `created_at`/`updated_at` columns managed by JPA auditing (`@CreatedDate`, `@LastModifiedDate`). Any `@DataJpaTest` that creates a `Category` must import `JpaAuditingConfig`:

```java
@Import({RepositoryTestcontainersConfiguration.class, JpaAuditingConfig.class})
class CategoryRepositoryTest { ... }
```

Without it, the NOT NULL constraint on `created_at` causes a `DataIntegrityViolationException`.
